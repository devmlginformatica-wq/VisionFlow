1. Visão Geral

A suíte cobre autenticação, clientes, pedidos, contas a receber e indicadores da Home. Os specs `*-real.spec.ts` exercitam a interface contra dados e endpoints reais da API Go, sem substituição da rede.

O Playwright abre a aplicação Vite em http://localhost:5173. No modo de desenvolvimento, chamadas relativas são encaminhadas pelo proxy do Vite para a API real, por padrão em http://localhost:8080. O alvo pode ser alterado com VITE_API_PROXY_TARGET.

Essa integração evidencia divergências de contrato que mocks podem ocultar. O relatório de apoio, RELATORIO_DIVERGENCIAS_E2E.md, registra incompatibilidades, riscos de estado do banco e os ajustes já identificados.

2. Pré-requisitos

  • Node.js e npm: o package.json não declara faixa em engines; use uma versão de Node compatível com Vite 8 e os pacotes do lockfile. O projeto tem package-lock.json.
  • Playwright: dependência de desenvolvimento @playwright/test ^1.64.1; instale também o browser Chromium. Em Linux, --with-deps instala dependências de sistema.
  • API: Go 1.25+ e API escutando em http://localhost:8080 (ou endereço compatível configurado no proxy do Vite). Consulte o README da API.
  • Banco: PostgreSQL 16 com migrations Flyway aplicadas. A configuração fica em visionflow-api/db/flyway.conf (copiada do exemplo local) e as migrations em visionflow-api/db/migrations/.
  • Seeds: os specs de leitura e os logins precisam dos dados de demonstração do tenant 4. O cenário está em visionflow-api/db/seeds/demo_comercial/ e pode ser aplicado por apply_all.sh em ambiente de desenvolvimento.

O compose.yaml define PostgreSQL 16 e um container de workspace, mas não define um serviço da API nem publica uma porta do Postgres para o host. Confira onde a API será executada e se o DB_HOST configurado consegue alcançar o banco. No modo Compose, a senha DB_PASSWORD deve estar definida para interpolação.

Para a API executada no host, o .env.example documenta as variáveis de conexão, PORT e JWT_SECRET. Copie para .env e configure valores locais; não reutilize segredos de produção.

Preparar banco, seeds e API

Na raiz de visionflow-api/, configure o ambiente local, aplique migrations e seeds de demonstração e inicie o servidor. O Flyway 13.7.0 é descrito no README da API. O script de seeds informa os requisitos de conexão e deve ser usado somente em desenvolvimento.

cd visionflow-api
cp .env.example .env
# Edite .env com valores locais para PostgreSQL e JWT_SECRET.
cp db/flyway.conf.example db/flyway.conf
# Configure a conexao local no flyway.conf.
flyway -configFiles=./db/flyway.conf info
flyway -configFiles=./db/flyway.conf migrate
./db/seeds/demo_comercial/apply_all.sh
go run ./cmd/api

Se o banco for recriado, db/scripts/reset_db.sh apaga os dados e aplica migrations; reaplique os seeds depois. Não execute esse script sem aceitar a perda dos dados do banco local.

409 ao criar endereço: confira o estado do banco Nesta sessão, o HTTP 409 RECURSO_DUPLICADO coincidiu com uma sequência PostgreSQL de códigos de endereço atrasada em relação aos códigos existentes. A sequência local foi sincronizada; isso é estado do banco, não mudança de código. Se o problema reaparecer, confirme o nome efetivo da sequência/tabela no ambiente antes de executar uma correção.

Para a estrutura local descrita nesta sessão, o comando idempotente abaixo posiciona o próximo valor após o maior codigo já armazenado. Execute apenas no banco de desenvolvimento correto:

SELECT setval(
  pg_get_serial_sequence('cliente_endereco_adicional', 'codigo'),
  COALESCE((SELECT MAX(codigo) FROM cliente_endereco_adicional), 0) + 1,
  false
);

O script visionflow-api/db/scripts/reset_db.sh recria o banco e aplica migrations, mas apaga todos os dados. Use somente em desenvolvimento e não o trate como rotina de correção para banco compartilhado; depois do reset, reaplique os seeds necessários.

3. Como Executar

Prepare primeiro o banco, migrations e seeds conforme o README da API. Suba a API Go em outro terminal com o banco acessível. A configuração atual da UI usa Vite como proxy; não é necessário apontar o browser diretamente para o serviço Go.

Instalação e suíte completa

cd VisionFlow
npm ci
npx playwright install
npm run test:e2e

Em Linux, instale browsers e dependências do sistema com npx playwright install --with-deps. A configuração do Playwright inicia npm run dev automaticamente em http://localhost:5173.

# Um arquivo real de cliente
npx playwright test tests/e2e/clientes-real.spec.ts

# Testes cujo título contém esta expressão

4. Arquitetura da Suíte

Fixtures

tests/e2e/fixtures.ts estende o fixture oficial do Playwright e exporta test e expect. O page vem do fixture Playwright padrão e herda o baseURL configurado. A função loginComo(email, senha) abre /login, preenche os campos por labels acessíveis, clica Entrar e aguarda a URL raiz. loginTenant4() e loginAdmin() são atalhos para contas de teste locais.

Helpers para API real

tests/e2e/real-api-helpers.ts lê o token de autenticação do localStorage do browser e constrói o cabeçalho Authorization para page.request; valida e desempacota respostas; extrai IDs; gera CPF/CNPJ com dígitos verificadores; e cria nomes e números de endereço dinâmicos. Também exporta:

  • createClientViaApi e createAddressViaApi para setup contra a API real;
  • deleteAddressViaApi para remover endereço real; somente HTTP 404 é tratado como já removido, e outros erros falham explicitamente;
  • listRealProducts para percorrer páginas do catálogo real, e formatBRL para asserções de moeda.
Regra para suítes de integração real Os specs `*-real.spec.ts` não devem usar page.route, MSW, interceptação de rede nem importar dados de src/mocks/. Configure dados reais via API, navegue pela UI e verifique persistência contra o servidor.
Exceção já existente no conjunto E2E crud/cliente-enderecos.spec.ts usa várias chamadas page.route e respostas simuladas para testar o contrato/comportamento isolado do editor de endereços. Portanto, não é um teste de integração com API real e não satisfaz a regra acima. A tabela de specs marca essa diferença; a decisão de migrá-lo ou mantê-lo como teste isolado fica como TODO de escopo, sem alteração neste guia.

Ciclo de vida recomendado

  1. Fazer login pelo fixture e, quando necessário, criar registros auxiliares via API real.
  2. Executar a ação principal pela interface usando nomes acessíveis e esperar respostas quando a chamada fizer parte da asserção.
  3. Verificar resultado na UI e, quando necessário, confirmar persistência com GET real.
  4. Limpar registros no afterEach/afterAll, sempre que possível com API real; tolerar apenas os casos explicitamente idempotentes, como DELETE 404 de endereço.

Nos specs existentes, o login e cleanup usam hooks por teste, compatíveis com o fixture page. Esse fixture tem escopo de teste; não o use diretamente em beforeAll/afterAll. Se o setup exigir interação com página, prefira beforeEach/afterEach ou crie e feche explicitamente um contexto de browser próprio.

Convenção: novos fluxos reais devem preferir tests/e2e/<fluxo>-real.spec.ts. Os diretórios crud/ contêm fluxos legados. Use getByRole, getByLabel e seletores existentes; regex ancorada como /^CEP/ evita que “CEP” encontre também o botão “Buscar CEP”.

5. Como Criar Novos Testes

  1. Escolha um fluxo de integração real como padrão. Teste de UI isolado é uma exceção explícita, não uma substituição silenciosa da API.
  2. Crie tests/e2e/<fluxo>-real.spec.ts.
  3. Para specs na raiz de tests/e2e/, importe { test, expect } de ./fixtures e os helpers necessários de ./real-api-helpers. Em crud/, o caminho relativo é ../fixtures.
  4. Faça login em beforeEach; crie pré-requisitos com helpers reais ou endpoints através de page.request e guarde IDs para cleanup.
  5. Limpe dados criados em afterEach/afterAll, tratando 404 como tolerável apenas quando a operação é idempotente e o helper já define esse contrato.
  6. Use seletores acessíveis, expect com espera explícita e dados únicos. Não use waitForTimeout.
  7. Para validar rede, crie a promise de page.waitForResponse antes da ação que dispara a requisição e confirme método, caminho e status reais.
  8. Execute o arquivo direcionado e, para diagnóstico visual, use --headed e --trace on.

Esqueleto: listar produtos reais

Exemplo mínimo para arquivo novo na raiz de tests/e2e/. Reusa imports/funções existentes. Como essa leitura não cria recursos, não precisa de cleanup; o fixture de autenticação é aplicado por teste. Os specs atuais usam beforeEach/afterEach quando precisam de page, não beforeAll/afterAll.

import { expect, test } from './fixtures'
import { listRealProducts } from './real-api-helpers'

test.describe('Catálogo com API real', () => {
  test.beforeEach(async ({ loginTenant4 }) => {
    await loginTenant4()
  })

  test('lista produtos reais', async ({ page }) => {
    const products = await listRealProducts(page)
    expect(products.length).toBeGreaterThan(0)
  })
})

Se um teste criar cliente/endereço/pedido, acrescente estado de IDs e cleanup no hook de pós-teste conforme clientes-real.spec.ts ou pedidos-real.spec.ts. Não copie credenciais para um novo spec.

6. Boas Práticas e Armadilhas

  • Não use page.route, MSW ou importações de src/mocks/ em specs de integração real.
  • Não use waitForTimeout; prefira await expect(locator)... e espera de resposta com timeout padrão configurado pelo Playwright.
  • Evite labels parciais que colidem com nomes acessíveis de botões. Prefira getByRole('textbox', { name: /^CEP/ }) ou um ID estável existente.
  • Gere valores únicos por execução. O helper já gera documentos válidos e números de endereço dinâmicos; CEP precisa permanecer com oito dígitos.
  • Registre waitForResponse antes do clique. Verifique pathname e método com o formato realmente chamado.
  • Faça cleanup por API no hook apropriado, inclusive quando o teste falhar. Só ignore códigos como 404 quando o contrato do cleanup permitir explicitamente.
  • Prefira setup via API real (mais rápido) e validação do comportamento principal via UI. Confirme persistência no servidor quando o caso exigir.
  • Os fluxos legados e os novos specs reais coexistem. Não classifique um spec como integração real apenas por estar em tests/e2e/; confira se existe interceptação.
